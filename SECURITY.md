# Security Policy

## Purpose

The Developer Services Platform provides reusable infrastructure components for creating development, integration-test, demonstration, and experimentation environments on Proxmox.

The project is intended to help developers provision infrastructure quickly and consistently using technologies such as Terraform and Ansible.

It is **not a reference production architecture** and should not be interpreted as providing production-grade security assurance.

Successful deployment or testing using this platform does not demonstrate that the resulting infrastructure, or software tested on it, is secure or suitable for production use.

---

## Security Scope

Security is an important engineering objective of this project.

Where practical, the project applies security-oriented defaults and engineering practices such as:

* least-privilege configuration;
* explicit network segmentation;
* encrypted communications where supported;
* controlled secret handling;
* dependency and vulnerability scanning;
* pinned or otherwise controlled dependency versions;
* infrastructure-as-code review;
* automated validation and testing;
* software bill of materials generation where applicable;
* avoidance of default credentials;
* reproducible infrastructure configuration.

However, these measures do **not** constitute a security certification, formal security assessment, or guarantee that a deployed environment is secure.

Users remain responsible for evaluating the security of the resulting infrastructure for their own environment and use case.

---

## Intended Environment

This project is designed primarily for:

* software development;
* experimentation;
* demonstrations;
* prototyping;
* temporary or reusable developer infrastructure.

The project has not been validated as a complete solution for:

* production workloads;
* safety-critical systems;
* mission-critical services;
* high-availability environments;
* regulated production environments;
* environments processing sensitive or classified information;
* compliance with specific regulatory frameworks;
* disaster-recovery requirements;
* formal business-continuity requirements.
* integration testing;
* system testing;

Some individual components may themselves be suitable for production use, but the presence of such components does not make the overall platform a production-ready architecture.

## Production Use

The project's open-source license may permit use of the software in production.

Such use should not be interpreted as being recommended, validated, supported, or certified by the project maintainers.

Before using any part of this project in a production environment, users should independently perform appropriate activities such as:

* threat modelling;
* architecture review;
* security hardening;
* penetration testing;
* vulnerability assessment;
* capacity and availability analysis;
* backup and recovery validation;
* disaster-recovery testing;
* access-control review;
* secrets-management review;
* logging and monitoring review;
* dependency and supply-chain assessment;
* compliance assessment where applicable.

Production infrastructure should be designed, reviewed, deployed, and operated according to the requirements of the specific organization and system involved.

## AI-Assisted Development

This project intentionally makes use of AI-assisted software-development tools.

AI systems may contribute to activities including:

* code generation;
* infrastructure configuration;
* documentation;
* test generation;
* refactoring;
* architecture exploration;
* code review;
* security analysis.

AI-generated or AI-assisted output is treated as **untrusted engineering input**.

Where appropriate, contributions are subject to human review and automated validation before being accepted into the project.

Nevertheless, neither human review nor automated testing can guarantee that AI-assisted code is:

* correct;
* secure;
* complete;
* original;
* free of vulnerabilities;
* free of insecure assumptions;
* appropriate for a particular environment.

Users should therefore review infrastructure generated by this project in the same way they would review any other third-party infrastructure code.

See `AI_USAGE.md` for additional information about the project's use of AI-assisted development.

## Secrets and Credentials

Secrets must not be committed to the repository.

Examples include:

* passwords;
* API keys;
* private keys;
* access tokens;
* cloud credentials;
* VPN credentials;
* certificates containing private keys;
* production configuration containing sensitive information.

Example configurations should use placeholders or documented secret-injection mechanisms.

If a secret is accidentally committed, removing it from the current Git history is **not sufficient**. The affected credential should be considered compromised and rotated or revoked.

## Dependency and Supply-Chain Security

This project relies on third-party software including operating-system packages, containers, Terraform providers, Ansible collections, infrastructure services, and other dependencies.

A dependency being referenced by this project does not imply that the project maintainers provide any warranty regarding that dependency.

Users should independently evaluate third-party components and remain aware of:

* published vulnerabilities;
* upstream security advisories;
* unsupported software versions;
* compromised packages or container images;
* dependency provenance;
* license obligations;
* end-of-life announcements.

Where practical, the project may use automated dependency, vulnerability, SBOM, container, or configuration scanning.

Automated scanning is supplementary and must not be treated as proof that no vulnerabilities exist.

## Supported Versions

Security fixes are normally applied only to the current version of the repository.

| Version                      | Supported         |
| ---------------------------- | ----------------- |
| Current default branch       | Yes               |
| Previous commits or releases | Best effort       |
| User-modified deployments    | No formal support |

Because this project evolves rapidly, users should verify the current repository state before relying on earlier versions.

## Reporting a Vulnerability

Please do **not** publicly disclose a suspected security vulnerability through a GitHub issue before the maintainers have had an opportunity to investigate it.

Where available, use GitHub's private vulnerability reporting mechanism:

**Security → Advisories → Report a vulnerability**

If private vulnerability reporting is not enabled, contact the project maintainers through the private security contact method documented for the repository or organization.

A useful vulnerability report should contain, where possible:

* the affected component;
* affected version or commit;
* a description of the vulnerability;
* reproduction steps;
* prerequisites for exploitation;
* expected and observed behaviour;
* potential security impact;
* suggested mitigations, if known.

Please avoid including unrelated sensitive information.

---

## Vulnerability Handling

Reported vulnerabilities will be evaluated based on factors including:

* reproducibility;
* exploitability;
* affected component;
* expected deployment model;
* impact;
* availability of mitigations;
* upstream responsibility.

Where appropriate, the maintainers may:

* prepare a security fix;
* update affected dependencies;
* modify insecure defaults;
* add additional validation;
* publish a security advisory;
* coordinate disclosure with an upstream project.

A reported issue may also be determined to belong primarily to an upstream dependency rather than this repository.

---

## Security Boundaries

Users should not assume that deployment of this platform creates a trusted security boundary automatically.

In particular, deployments should independently consider:

* separation between development projects;
* separation between developers and platform administrators;
* management-network isolation;
* Proxmox administrative access;
* Terraform and Ansible credentials;
* container registry access;
* CI runner privileges;
* secrets-manager access;
* identity-provider administration;
* backup access;
* VPN access;
* service-to-service authentication;
* firewall policy;
* monitoring and audit logging.

Compromise of privileged infrastructure components may provide access to multiple development environments.

---

## Security Testing

Security-related checks may include automated testing, static analysis, vulnerability scanning, infrastructure validation, configuration checks, and manual review.

These checks are intended to reduce risk.

They do not constitute:

* a formal penetration test;
* an independent security audit;
* a security certification;
* proof of compliance;
* proof that the infrastructure is free from vulnerabilities.

---

## Responsible Use

Users are expected to review the generated infrastructure configuration before deployment and adapt it to their environment.

Security-sensitive defaults should not be assumed to remain appropriate when the architecture, networking model, threat model, software versions, or operational context changes.

The ultimate responsibility for operating a secure deployment remains with the organization deploying and operating the infrastructure.
